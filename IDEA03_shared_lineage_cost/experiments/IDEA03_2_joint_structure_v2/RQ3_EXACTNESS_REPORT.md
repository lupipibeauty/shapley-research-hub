# RQ3 精确性与语义核验报告

## 1. SQL 与 Python evaluator

有效 E0 对 N=10、16 的 Low/High 完整枚举全部联盟：

- 联盟数合计：133,120。
- SQL 报表行：931,840。
- 逐坐标比较：4,659,200 项。
- 不一致：0。

比较覆盖空联盟、满联盟、所有单玩家联盟及全部其余联盟。NULL 比较采用“双方均为 NULL 才相等”，没有把 NULL 静默改为0。

E1 和 E2 的 SQL 层分别对每个 fixture 使用冻结的64个联盟掩码，包含空、满、单玩家、单玩家缺失和固定随机样本。E1 的 Shapley oracle 仍基于完整 `2^20` 价值表；SQL 样本仅用于避免重复执行数百万行 SQL。

## 2. Shapley exactness

E0 中 H3-S6 evidence-state 方法与全联盟 NumPy oracle 的最大玩家绝对误差为 `2.274e-13`。E1 三个 N=20 配对、四个价值、Low/High 全部通过，最大误差为 `1.592e-12`，低于冻结容差 `1e-9`。

所有通过单元同时满足效率检查。`lambda=0` 时，local/cross 的 joint 价值数组与对应 add 价值数组逐元素严格相等。

E1 另对 seed 9201 的 High/cross-add 执行“两坐标分别编译后按线性合并”。合并分配相对全联盟 oracle 的最大误差为 `5.258e-13`。

## 3. 归一化与金额映射

主成本实验使用 Low/High 配对共同的满报表最大值作为参考尺度，固定收入 R=1000、lambda=0.5。各结构自身满报表归一化的分配作为补充结果保存在 `shapley_allocations.csv`，字段 `reference_mode=structure_own`；它不与主成本四格混算。

## 4. 未获精确性资格的部分

N=24 没有全联盟 oracle。修正后的 E2 只证明输入语义和报表状态非退化；H3-S6 在编译阶段达到状态上限，未产生 N=24 分配。因此不得把 E2 写成“精确求解成功”。

P3 MTBDD、LExaShap/Abramovich 归约、通用 BDD/d-DNNF 和 M3 本轮均未完成同一冻结输入的可执行适配，不能使用历史报告替代当前 exactness 证据。
