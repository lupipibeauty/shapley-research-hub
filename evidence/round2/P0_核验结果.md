## P0-02：GNN 玩家→物理事实映射

映射的构造代码在 `course_paper_gnn/src/course_paper_gnn/tpch.py`：

- 第 198–330 行的 `build_player_relations_from_rows` 直接创建 `o:<orderkey>`、`c:<custkey>`、`l:<orderkey>:<linenumber>`、`s:<suppkey>`、`n:<nationkey>` 五类玩家；`relation_key` 保存物理键，`links` 保存 lineitem 到 order/supplier/nation 的连接。
- 第 333–410 行将玩家、所选 lineitem ID 和游戏元数据写入 `GameRecord`。
- `schema.py` 第 10–29、145–173 行规定 JSONL 中 `players`、`relation_edges`、`metadata` 的保存格式。

冻结训练数据 `course_paper_gnn/data/final/tpch_g1000_v2.jsonl` 第一条 `tpch_sf01_69248` 给出可直接读取的实例：

| player_id | relation / relation_key | owner_id | 物理事实与链接 |
|---|---|---|---|
| `o:69248` | order / `69248` | `customer:12781` | orders 的 `o_orderkey=69248` |
| `c:12781` | customer / `12781` | `customer:12781` | customer 的 `c_custkey=12781` |
| `l:69248:1` | lineitem / `69248:1` | `supplier:362` | lineitem `(l_orderkey,l_linenumber)=(69248,1)`；链接 `o:69248`,`s:362`,`n:23` |
| `s:362` | supplier / `362` | `supplier:362` | supplier 的 `s_suppkey=362`；链接 `n:23` |
| `n:10` | nation / `10` | `nation:10` | nation 的 `n_nationkey=10` |

该游戏的 metadata 还列出 `selected_lineitems=[l:69248:1,…,l:69248:4]`。因此“订单与订单行因关联而自动属于同一玩家”的说法不成立：该实例中它们是不同 player_id；只是其来源图以 lineitem→order 边连接。当前数据文件 SHA-256 为 `EED6FF929270CBB6736A281037A4CFE3C9470D9F8AB9CBD423F9FAD85350AEC3`。

**保留缺口：**没有单独命名的 player-to-fact CSV、数据生成时的输入数据库哈希或每个游戏的外部 SQL 主键快照；现有映射足以核验冻结 JSONL 内的玩家绑定，但不足以重建原始 DuckDB 的整个抽取生命周期。

## P0-03：GNN 边方向与消息传递

`course_paper_gnn/src/course_paper_gnn/graph.py` 第 170–175、221–299 行只构造：

```text
player → witness → coordinate → value_factor → report
```

`data.py` 第 112–140 行把每个 `edge.source, edge.target` 原样写入 `edge_index`，没有 `to_undirected`、反向 edge type 或自动双向化逻辑。`model.py` 第 40–59 行中，消息是 `hidden[selected_source]`，再用 `index_add_` 累加到 `selected_target`，即沿上述正向传播。`model.py` 第 195–204 行从图池化 context 与玩家自身隐藏状态构造贡献头。

第一条冻结游戏含 43 条边，所有边同样为正向；未找到反向边记录。**可核验判断：两层图层可使 witness/coordinate/factor/report 获取上游玩家信息，但玩家节点只保留自投影，不能经这些图层接收下游 witness 信息。** 图级池化仍可将全图 context 提供给每个玩家贡献头。未做运行时前向 trace，故结论以代码和冻结 edge list 为依据。
