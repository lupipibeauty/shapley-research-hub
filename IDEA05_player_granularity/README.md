# IDEA05：玩家粒度与所有者分配

## 1. 研究问题

数据库物理记录如何绑定为 Shapley 游戏中的玩家或事实包？记录粒度、来源关系和所有者分配的不同选择，是否会改变贡献解释？

## 2. 探索过的方向

审计重点核验了 GNN 游戏生成器中的玩家映射，而不是根据数据库外键自行推断玩家。冻结 JSONL 中包含 `players`、`relation_key`、`links` 与 `metadata`；可以核验不同 `player_id` 的绑定事实，但仍缺独立导出表。该问题与 IDEA01 的报表价值定义、IDEA04 的图构造相关，但不能用 GNN 结构替代玩家语义定义。

## 3. 实验设计与目的

未来应冻结同一游戏生成器，仅改变玩家绑定规则，比较精确 Shapley 分解、效率性、玩家排序和下游模型表现。每个事实包的加入／退出必须追溯到生成规则和物理记录清单。

## 4. 实际完成度

已完成映射代码和冻结 JSONL 的存在性核验；尚未形成每游戏独立的玩家—事实 CSV、输入数据库哈希或外部 SQL 主键快照。因此 IDEA05 仍是候选问题。

## 5. 停止／阻塞原因

不能仅凭订单与订单行的关联认定同一玩家；缺少可独立审阅的绑定清单；重新定义玩家会同时改变价值函数和训练数据，不能作为普通后处理。

## 6. 下一步边界

优先导出玩家—事实映射及生成配置；在映射得到确认前，不运行新的粒度对照，也不把推测写入实验结论。
