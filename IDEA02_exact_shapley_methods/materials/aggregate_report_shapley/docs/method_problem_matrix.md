# v4.0 既有 Shapley 方法复现与适用性检验矩阵

本表登记待检验问题，不预先宣告旧方法错误或项目已有创新。v4.0 将 S1 价值性质审计、R0 真实复现和 R1 同目标适配列为核心证据；owner 游戏、层次值和 Jiang 适配仍不是标准记录级 R-game 的直接性能基线。

|---|---|---|---|---|---|
| P1 | 单查询 tuple Shapley | 单坐标查询不能直接代表非线性整表 `G(Y)` | V1 逐坐标合成对整表直接计算；V2 交互 | S1/R1/S2 | V1 必须精确复原；V2 不预设可分解 |
| P2 | 每个物理 tuple 都是玩家 | 基本行、属性行或连接复制行拆散同一逻辑记录包 | SQL-P/SQL-U/ST 与逻辑玩家数 | S0/S1 | 玩家恒为12个记录包；维度外生、属性随包激活 |
| P3 | 把记录支付按 owner 相加称为 owner Shapley | 付款汇总与 owner 联盟游戏混淆 | `aggregate_record_payments` 对未来 O-game | S1/后续 | S1 只输出付款汇总，不计算或命名为 owner Shapley |
| P4 | 从报表树自动生成玩家层次 | `H_report` 与 `H_player` 不是同一对象 | 报表层次说明对 Besner 假设 | 文献参考 | S0/S1 不运行层次值 |

## 文献适用性状态

- `DIRECT`：模型和输入直接满足方法定义；
- `REDUCIBLE_EXACT`：通过明确、保持目标的精确归约后适用；
- `THEORY_ONLY`：理论可用于边界判断，但未运行实现；
- `ASSUMPTION_NOT_MET`：指出具体不满足的前提；
- `UNVERIFIED`：证据或代码尚不足，不能下结论。

## 差异归因顺序

1. 检查记录身份、SQL 粒度、空值、连接和去重；
2. 检查输入报表、玩家、价值函数和参数是否相同；
3. 检查联盟价值表是否一致；
4. 检查精确 Shapley 实现；
5. 检查第三方原目标是否已真实复现、适配器是否保持目标；
6. 仅在同目标实现一致后讨论性能瓶颈；
7. 对异常构造最小案例并按接口、实现、假设或资源失败分类；
8. 仅在文献归约、官方实现能力和普通数据库解释均排除后讨论候选研究问题。

该顺序防止把查询错误、游戏变化或未运行代码包装成 Shapley 算法缺陷。
