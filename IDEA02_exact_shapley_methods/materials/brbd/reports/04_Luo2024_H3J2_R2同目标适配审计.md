# Luo（2024）H3-J2 R2 同目标适配最小验证

## 1. 实验定位

本轮不是把 H3-JV 的完整 35 坐标报表直接声称为 Luo 原生输入，而是检查 Luo RDSV 是否能够在保持 H3-JV 玩家和 JOIN witness 不变的前提下，处理其中可加的跨玩家 JOIN 子游戏。

H3-JV 的 J2 为 `R(x), S(x,y), T(y)` 三方连接，固定 12 个逻辑玩家、8 个 JOIN grounding、4 个 distinct key。Luo 官方前端不能直接读取 H3 的关系模式，也不能直接表达整表 `COUNT DISTINCT`、比例评分或 V2 几何联合价值。因此本轮采用透明的适配器：将每个 H3 J2 grounding 嵌入一条相互隔离的 TPC-H 连接链，由作者原生 TPC-H join plan 生成同一个 Boolean conjunction。

## 2. 固定对象

- H3-JV seed：7301。
- 玩家：`p1`--`p12`，保持原逻辑记录身份。
- 查询结构：J2 三方跨玩家 JOIN。
- 子游戏：7 个层次节点 × 3 个可加统计量。
- 统计量：`bag_count`、`amount_sum`、`target_count`。
- 子游戏总数：21。
- 官方程序：Luo checkout commit `2a514fb4a0e3d45365d6dffe6435f93499afd7e3` 的 `cal_sv_rust1.75_release.exe`。
- 执行：Windows、Rust 1.75 GNU release、单线程、作者 `rdsv` 模式。

`COUNT DISTINCT` 未放入本轮，因为同一业务 key 的多个 grounding 需要 Boolean OR，不能由作者当前 TPC-H 原生前端的“每个 joined tuple 一个简单游戏”直接表达。V1 比例和 V2 几何联合价值也未放入，因为它们不是独立输出效用。

## 3. 输入构造

脚本：

`runs/BRBD_v1/scripts/generate_h3_j2_luo_r2.py`

对每个 H3 J2 grounding 构造一条唯一键的八表 TPC-H 链：

```text
region → nation → supplier → partsupp → part
        → lineitem → orders → customer
```

三条承载边分别放置 grounding 的玩家；其余表重复最后一个玩家，使连接结果的 owner conjunction 与 H3 grounding 完全相同。`amount_sum` 使用 bag 复制实现整数权重，未把权重写入算法答案。

第一次运行暴露了一个适配器错误：金额权重只写入 manifest，未复制为 bag 行，导致效率性不一致。错误结果和日志保存在 `runs/R2_h3_j2_luo/invalid_frontend/`，修正后仅重跑金额子游戏并保留 retry 命名。

## 4. SQL 与来源核验

对 21 个数据集独立执行 DuckDB 八表 JOIN。预期扩展行数、实际 JOIN 行数全部一致：

- 21/21 个子游戏通过；
- `sql_grounding_validation.csv` 中 `match=true`；
- 没有从完整联盟真值构造输入。

该 SQL 核验只确认适配器产生的关系 JOIN 与 grounding 数量一致，不把合成 TPC-H 表称为原始 H3 SQL 数据库。

## 5. RDSV 正确性

每个子游戏先由 grounding 闭式独立计算记录级 Shapley：对 grounding 玩家集合 (W_g)，每个 (i\in W_g) 获得 (w_g/|W_g|)。再与 Luo 官方 RDSV 输出逐项比较。

- 21/21 子游戏通过；
- 每个子游戏支付总和等于其满联盟权重；
- 最大逐玩家绝对误差不超过机器舍入范围，CSV 中为 0；
- 组合后的 21 坐标加权和支付总和为 1000；
- 组合后的最大绝对误差为 0，L1 误差为 0。

组合定义为：

\[
G_{J2,21}(S)=\frac{1000}{21}
\sum_{c\in C_{21}}\frac{T_c(S)}{T_c(N)},
\]

其中 (C_{21}) 是 7 个节点上的三个可加统计量。该组合是本轮明确冻结的 R2 子游戏，不等同于历史 H3 的完整 G0/G1/G2。

组合记录级结果见：

`runs/R2_h3_j2_luo/r2_combined_g0_21_shapley.csv`

## 6. 计算成本

作者二进制对 21 个微型子游戏均成功完成。由于每个子游戏只有 1--32 个展开 grounding，求解时间处于毫秒级，端到端成本主要由 Polars 数据加载和 JOIN 初始化构成。这个规模不能用于与 TPC-H SF=0.1 的 500-owner 性能直接比较，只能作为接口和目标一致性关卡。

完整逐次成本见：

`runs/R2_h3_j2_luo/r2_correctness.csv`

## 7. 适配结论

### 已验证

1. H3 J2 的跨玩家 grounding 可以在保持玩家身份的前提下，归约为 Luo 支持的独立简单游戏集合。
2. 对 `bag_count`、整数权重 `amount_sum` 和筛选后的 `target_count`，官方 RDSV 可以计算同一记录级 Shapley 目标。
3. 归约输入没有读取 4096 个联盟支付，也没有用已知 Shapley 答案构造输入。

### 尚未验证

1. `COUNT DISTINCT` 的多 grounding OR 合并是否能由 Luo 官方接口原生接收。
2. 完整 35 坐标 G0 的 distinct 组件是否能保持同一目标并自动编译。
3. V1 比例评分和 V2 几何联合价值是否能避免完整联盟枚举。
4. 多指标共享来源在中等规模下是否降低或增加端到端成本。

## 8. 下一关建议

下一关不应直接扩大玩家数，而应构造一个最小 `J2-DISTINCT` 适配器：保持两个 grounding 共享同一业务 key，分别验证 bag 计数、Boolean OR 和记录级 Shapley。若官方 Luo 前端仍无法直接表达，应把结论登记为“数学上可归约、当前官方接口不支持”，再决定是否为 RDSV 后端增加独立 DNF 输入适配器。
