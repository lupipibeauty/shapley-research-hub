# 03 成本分解及性能对照

所有数字来自同一 Python 3.11.6 进程环境的 3 次确定性重复，报告中位数与 IQR。模块导入成本不在流水线内；RSS 是全进程采样峰值，不是算法增量内存。

## 主要结果

| 路线/阶段 | 中位数（秒） | IQR（秒） |
|---|---:|---:|
| LExa fixture→H1/H2 DNF | 0.00114 | 0.00034 |
| LExa H1 独立编译并求全部玩家 | 0.06250 | 0.00088 |
| LExa H2 独立编译并求全部玩家 | 0.01241 | 0.00271 |
| LExa 端到端 | 0.07567 | 0.00372 |
| MTBDD 数据库 schema/load | 0.08541 | 0.87338 |
| MTBDD SQL witness 提取 | 0.00416 | 0.01408 |
| MTBDD 编译 | 0.00977 | 0.00127 |
| MTBDD 全玩家条件模型计数 | 0.02095 | 0.00118 |
| MTBDD G1 求解 | 0.00292 | 0.00026 |
| MTBDD 端到端 | 0.13317 | 0.88793 |

进程峰值 RSS：LExa 流水线约 114.0 MB；MTBDD/DuckDB 流水线约 182.1 MB。两者包含不同运行时状态，不能解释为纯数据结构占用差。

## 表示规模与共享

- P3 MTBDD：367 个非终端节点、9 个 `(q_A,q_B)` 终端。一次联合状态编译可支持 G0/G1 和全部 13 玩家条件计数。
- LExa H1：21 个 d-tree 节点、60 个 Value 图节点。
- LExa H2：5 个 d-tree 节点、21 个 Value 图节点。
- H1/H2 通过两个独立 `DNFCircuit` 编译；当前官方单 DNF 接口没有跨游戏共享子表达式。

在这个实例中，SQL→DNF 不是主要成本，H1 独立编译/求解占 LExa 路线的大部分；MTBDD 路线的端到端波动主要来自首次 DuckDB schema/load。去掉数据库启动后，MTBDD 的核心编译、条件计数和 G1 求解约为数十毫秒，与 LExa 同处小实例量级。

不能据此宣称某方法一般更快：只有一个 13 玩家实例，而且两条路线的前端不同。当前证据只能说明瓶颈位置，不是复杂度优势。
