# 05 算法覆盖与创新缺口判断

## 当前实验做到的层次与复杂度

当前主线已经到达：三张内生关系表、13 个物理事实玩家、6 个跨玩家 JOIN witness、两组 `COUNT(DISTINCT entity_id)`、整表 `G1=min(q_A,q_B)`、8192 联盟真值和 1000 元记录级支付。算法层面同时具有：367 节点的经典 MTBDD 联合状态路线，以及 H1/H2 的官方 LExaShap 归约路线。C2 另有一个城市—省级和地区×行业的最小语义实验，但它尚未进入 P3 主游戏的 Shapley 性能测试。

这仍是固定小实例：没有扩大玩家数，没有增加统计组或报表层次，没有形成参数化宽度族。因此目前只能判断正确性、表示规模和成本构成，不能给出一般复杂度或扩展性结论。

## RQ 回答

1. **RQ1：G1 是否已被既有方法解决？** 是。当前 G1 被两条经典路线精确解决：MTBDD 直接维护 `(q_A,q_B)`；LExaShap 通过 H1/H2 Boolean 分解归约。C1 在当前锚点上属于 `REDUCTION_COVERED`，没有新算法缺口。
2. **RQ2：SQL witness→DNF 是否为主要成本？** 当前不是。转换中位数约 0.00114 秒，远小于 H1 编译/求解约 0.06250 秒。但 9/4 子句太小，不能外推到一般最小获胜集合构造。
3. **RQ3：H1/H2 是否共享？** 当前官方接口分别编译，未跨游戏共享。MTBDD 一次保存联合计数状态，能够复用到多个效用。这是可测的实现差异，但知识编译、多输出电路和批量查询共享都是强竞争方法，不能直接称为创新。
4. **RQ4：C2 需要什么信息？** 局部计数不足；需要实体身份及其跨层/交叉来源关系。现有 provenance 与因式化数据库理论覆盖语义基础；ProvSQL 紧凑度仍未实测。
5. **RQ5：是否已有新算法的必要证据？** 尚不能确认。当前困难已被归约或属于接口/环境/表示成本问题。

## 是否启动参数化性能实验

**暂不启动大规模参数化实验。** 当前唯一可保留的最小问题是：当组数和阈值数增加但 SQL/玩家保持受控时，分别编译多个 `H_t` 与联合多值电路的表示规模差异是否可由已有多输出知识编译完全消除。下一步应先做 3–4 个手工构造的小型共享结构实例，并加入 d-DNNF/AMC 或 ProvSQL 强基线；只有出现可复核、非接口造成的表示瓶颈，才值得建立规模族。

C2 的下一步则是搭建 ProvSQL 1.13.1 隔离环境，验证父级 DISTINCT 与共同输入令牌是否真实保留。若能正确、紧凑表示，C2 应继续判定为已有方法覆盖。
