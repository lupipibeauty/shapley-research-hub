# P3-0 原生精确计算可行性

## 结论

已实现一条不以 8192 个联盟真值为输入的经典精确路线。算法从三张事实表的实际 JOIN witness 出发，生成每个实体的 DNF 资格来源，编译为按 13 个玩家排序的分层多终端决策图（layered MTBDD），再计算联盟大小与 `(q_A,q_B)` 的精确联合计数。

对每个焦点玩家 `i`，分别强制 `i=0` 和 `i=1`，得到其余 12 个玩家的条件分布 `C_i^0(k,a,b)` 与 `C_i^1(k,a,b)`。标准 Shapley 直接由

`sum_k k!(n-k-1)!/n! * sum_(a,b) [C_i^1(k,a,b)-C_i^0(k,a,b)] G(a,b)`

求得。因为每个变量层都被保留，不需要对跳过变量作隐式组合数修正。联合分布可在 G0/G1 之间共享，但本轮仍逐玩家做两次条件计数，没有宣称已实现一次反向传播的全玩家最优方案。

## 正确性结果

- 13 玩家、8192 个联盟的 DuckDB SQL 与独立 Python 语义逐项一致。
- 满联盟 `(q_A,q_B)=(2,2)`，`G0=4`，`G1=2`；空联盟均为 0。
- 原生 MTBDD 具有 367 个非终端节点和 9 个联合终端，全局计数和为 8192；每个焦点玩家的每个强制值分布都精确包含 4096 个其余玩家联盟。
- G0/G1 的 13 个 Shapley 同时与子集公式和 Möbius/Harsanyi 实现完全一致，且效率性精确成立。
- 4 个单元测试全部通过，包括 SQL/Python 全联盟、来源结构、三重 Shapley 真值、收入守恒。

时间是当前单次环境审计，不是复杂度结论。数据库初始化包含 DuckDB 连接/schema 成本，因此显著大于小型算法核心。进程 RSS 峰值已修复为 Windows API 实测；在原生路线中约 133.5 MB，它包含 Python、DuckDB 和已经载入的全进程基线，不是 MTBDD 的纯增量内存。详细数据见 `results/native_method_costs.csv`。

当前小例中，真正的算法核心成本在“编译 + 全玩家条件计数”，而不在 G0/G1 数值评价。但 13 玩家不足以判断一般瓶颈；节点数随变量顺序和来源宽度的增长尚未实验。

## 方法边界

1. 当前实现是经典 OBDD/MTBDD 与按基数加权模型计数的适配，不是新算法。
2. 367 节点小于 8192 联盟仅证明该实例可压缩，不证明一般多项式可处理性。
3. 当前条件分布对玩家重复遍历同一图；反向求导/全玩家共享是后续可审计的工程或算法问题，但尚未构成新颖性证据。
4. 正确性 oracle 在原生结果产生后才执行，不参与图构造或输入。
